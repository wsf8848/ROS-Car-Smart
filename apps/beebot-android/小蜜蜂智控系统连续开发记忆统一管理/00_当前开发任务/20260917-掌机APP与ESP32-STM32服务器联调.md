## 检查点 4：掌机覆盖安装与 WSS/MQTT 复验

- 状态：已完成连接与上行验证，发现下行重启序号问题（2026-09-17，Asia/Shanghai）。
- `adb install -r` 成功，设备端确认 versionCode 35 / versionName 2.6.1；冷启动 Activity 正常，无本应用 FATAL。
- 冷启动后主页显示“车辆在线”，不再显示“MQTT 配置缺失”；`BeeBotMqtt` 无 TLS、认证或连接异常，证明 APP -> WSS Broker -> ESP32 状态链路恢复。
- STM32 上行遥测持续显示 `12.5V / 97%`、四轮脉冲 `0 0 0 0`；短时间内 MQTT 遥测计数由 133 增到 622、解析帧由 399 增到 1866、ESP32 UART 帧由 52084 增到 57334，证明 STM32 UART4 -> ESP32 -> Broker -> APP 上行链路稳定。
- App 重启后状态仍显示 ESP32 最后命令 `0x49`，但业务延迟持续“刷新中”，说明新进程发出的停车探针没有获得新序号回执。
- 根因证据：APP 的 `nextControlSequence` 是进程内变量，每次启动重置为 0；ESP32 在已有序号时只接受模 256 前向差值 1..127，因此重启后的 0 可能被判为 stale。之前同一次 v2.6.1 会话曾显示 139ms RTT 和 `0x5E` 回执，排除发布接口整体失效。
- 安全结论：当前只验证了旧 `0x49` 状态和上行 UART 遥测，不能把它冒充本次新进程的下行停车 ACK。
- 下一步：APP 持久化下一个控制序号；ESP32 仅允许完整合法的 `0x49` 停车帧安全重同步序号，其他 stale 命令继续拒绝，然后重新构建、烧录和复验。

- 状态：代码与构建已完成，待烧录装机复验（2026-09-17，Asia/Shanghai）。
- APP：使用私有 `mqtt_control_state` 保存 `next_control_sequence`，每次 QoS0 发布成功后推进并异步持久化；初始化从持久值恢复，不从可能延迟的状态回执反向校准。
- ESP32：完整长度、头尾、版本、保留区、CRC 和白名单均通过后，只有命令 `0x49` 可以在 stale/duplicate 序号时重同步窗口；其他命令继续执行原前向差值 1..127 规则。

- 下一步补充：将待确认时间戳移到发布调用前，发布失败时回滚，并记录不含凭据的 ACK 命中诊断，然后复验 RTT。
