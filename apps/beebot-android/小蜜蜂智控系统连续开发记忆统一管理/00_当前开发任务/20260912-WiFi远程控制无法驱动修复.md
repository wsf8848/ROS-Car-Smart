# 2026-09-12 WiFi 远程控制无法驱动修复

## 任务目标

- 针对 STM32 V2.6 已烧录后，APP 切换到 WiFi 远程仍无法控制车辆的问题，定位 APP -> MQTT -> ESP32-C3 -> UART4 -> STM32 的实际断点并修复。
- 保留蓝牙手动控制、失联停车和当前遥测回显，不以降低车端安全保护换取控制。

## 基线与保护边界

- APP 基线为 v2.2.0 / versionCode 28；工作区含大量既有未提交和未跟踪内容，本轮只做增量修改。
- STM32 用户确认 V2.6 已下发；下载动作不再作为本轮假设边界，但仍需用收发证据区分是否真正收到 UART4 控制。
- 用户要求 STM32 下载使用 DAP，禁止改用 J-Link。

## 检查点 1：链路审计

- 状态：完成。
- 三端枚举正常：Retroid `SN0004753`、ESP32-C3 `COM8`、Horco CMSIS-DAP `507874111264`。
- 现场主控显示车辆在线、RTT 约 100ms、电源/雷达/底盘遥测持续更新；ESP32 串口确认 UART4 三类遥测持续有效，因此回显上行链路正常。
- APP 冷启动后 ESP32 正确接受 `0x49 x3 -> 0x5B`，说明 MQTT 主题、20 字节帧、CRC、模式授权和 ESP32 到 STM32 UART TX 均已进入有效路径。
- 注入前进摇杆后，ESP32 连续接受 `0x41`，但每帧后立刻输出 `motion control timeout exceeded 300 ms` 并向 STM32 发送 `0x49 x3`。
- 根因：ESP32 `loop()` 在 `mqttClient.loop()` 之前保存 `now`；MQTT 回调使用更新后的 `millis()` 写入 `lastMotionControlMs`，随后旧 `now - lastMotionControlMs` 发生 uint32 下溢，误判超过 300ms。
- APP 的车辆 freshness 门控不是本次直接原因：复现时车辆在线且所有 `0x41` 均被 ESP32 接受。

## 检查点 2：ESP32 看门狗时间修复

- 状态：完成。
- 修复策略：处理 MQTT 回调后重新读取 watchdog 当前时间，再执行 300ms 运动超时判断；保留掉线、非法帧和真实超时停车。
- 固件使用 ESP32-C3 Skill 的本机缓存构建：RAM 40,460 / 327,680（12.3%），Flash 896,470 / 1,310,720（68.4%）。
- COM8 烧录成功，芯片为 ESP32-C3 rev 0.4、4MB XMC Flash，bootloader、分区表和应用段均 Hash 校验通过。
- 最终 `firmware.bin` 为 917,952 字节，SHA-256 `35B1E52025893D0045143B78390FD4836C492DEA62BBE4D019E0A2B2CE1E40C0`。

## 检查点 3：三端实机闭环

- 状态：完成。
- 正常前进期间连续 `0x41` 被 ESP32 接受并送往 STM32，期间没有误触发 `[SAFE]`。
- STM32 返回非零四轮遥测 `55 52 1C 1C 19 1A 00 5B`，证明车轮已经实际执行。
- 摇杆回中和 A 键均恢复 `0x49` 停车。
- 运动中强制停止 APP：最后运动帧 9.517s，ESP32 在 9.819s 发三连停车，约 302ms；STM32 350ms 保护仍保留。
- APP v2.2.0 和 STM32 V2.6 无需改动；本轮唯一业务代码改动为 ESP32 `src/main.cpp` 的看门狗判定时间。
