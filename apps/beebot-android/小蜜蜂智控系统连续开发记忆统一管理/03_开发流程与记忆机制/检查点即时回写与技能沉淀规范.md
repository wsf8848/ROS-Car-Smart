# 检查点即时回写与 Skill 沉淀规范

## 目标

确保任何会话中断、电脑重启或上下文压缩后，都能从工程内记忆恢复到最近一个已验证检查点，而不是依赖聊天历史。

## 开始任务

每次开始新开发任务时立即执行：

1. 读取 `README_总索引.md`、最新当前任务和项目基线。
2. 检查 `git status`，记录已有改动与保护边界。
3. 在 `00_当前开发任务` 新建 `YYYYMMDD-任务名.md`。
4. 在总索引登记为“进行中”，写清目标、非目标、计划检查点和当前风险。
5. 完成上述写入后才开始修改代码。

## 检查点定义

检查点必须是可验证的阶段结果，例如：

- 基线和需求审计完成。
- 一个页面静态 UI 完成并通过预览。
- 一个模块编译通过。
- APK 安装成功。
- APP 启动且目标进程存活。
- 页面截图验证通过。
- 实体按键/摇杆输入验证通过。
- MQTT 登录、订阅或发布验证通过。
- ESP8266 收包、失联停车或遥测回传验证通过。
- 问题根因得到证据支持。

“尝试了一下”“应该可以”不算完成检查点。

## 每个检查点立即写入的字段

```markdown
### 检查点 N：名称

- 开始/完成时间：
- 目标：
- 实际改动：
- 执行命令或测试：
- 可核验结果：
- 遇到的问题与失败尝试：
- 根因与解决方法：
- 未验证边界：
- 下一步：
- 状态：完成 / 失败待处理 / 阻塞
```

完成检查点后，先写记忆，再进入下一检查点。不得把多个检查点积压到会话末尾一次补写。

## 问题记录规则

遇到问题时采用四阶段记录：

1. **现象**：原始报错、可见行为、发生条件和影响范围。
2. **失败尝试**：做了什么、为什么无效，防止后续重复踩坑。
3. **根因**：代码、协议、设备、环境或流程层面的证据。
4. **修复与验证**：最终改动、复现是否消失、有哪些硬件边界仍未验证。

问题具有跨任务复用价值时，在 `05_问题修复与技能沉淀` 建立独立记忆，并同步更新项目 Skill。

## Skill 沉淀规则

更新目标：`C:\Users\Bee\.codex\skills\xiaomifeng-robot-controller\SKILL.md`。

应写入 Skill：

- 会影响后续技术决策的稳定事实。
- 已被真实验证的设备/ROM/编译/安装坑。
- 已确认的协议映射和安全约束。
- 可重复使用的排查顺序和验证命令。
- 用户长期要求的 UI 先确认、检查点即时回写、验证通过再发版规则。

不应写入 Skill：

- 一次性时间戳和长篇终端日志。
- 未经验证的猜测。
- 已过期但没有标记的结论。
- MQTT 密码、签名密码、证书私钥等秘密。
- 只属于单次任务的细枝末节。

每次更新 Skill 后运行 `quick_validate.py`，校验通过后再将任务记忆的 Skill 检查点标记为完成。

## 验证层级

必须分开记录，不能用低层验证冒充高层验证：

1. 静态检查/代码审阅。
2. Kotlin/Gradle 编译。
3. Release APK 生成与签名。
4. 目标设备安装。
5. APP 启动、进程和崩溃日志。
6. 页面布局与交互截图。
7. Retroid 实体摇杆、按键、震动和语音。
8. MQTT 公网连接、发布、订阅、重连和时延。
9. ESP8266 收发、串口桥和失联保护。
10. 真车低速、安全场地端到端验证。

## 完成任务

只有所有约定检查点完成后：

1. 更新任务记忆的最终结果、验证边界和下一入口。
2. 更新项目基线及总索引状态。
3. 将可复用问题补充到问题分类和 Skill。
4. 更新版本号、README、CHANGELOG 和最新 APK。
5. 验证无误后再 commit、tag、push；验证失败不推送。
