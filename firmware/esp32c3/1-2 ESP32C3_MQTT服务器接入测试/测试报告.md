# ESP32-C3 MQTT 服务器接入测试报告

测试日期：2026-09-12  
测试结论：**通过，可作为后续车端 MQTT 接入基线。**

## 1. 测试对象

- 开发板：ESP32-C3 Super Mini，4 MB Flash
- 实测串口：COM8
- 板载 LED：GPIO8，低电平点亮
- MQTT 协议：MQTT 3.1.1 over TLS
- 服务器：`43.138.223.90:8883`
- 控制主题：`car/001/control`
- 遥测主题：`car/001/telemetry`
- 状态主题：`car/001/status`
- 控制与遥测测试帧：固定 20 字节二进制数据

账号、密码及 Wi-Fi 密码没有写入源码或本报告。编译前脚本从服务器配置文件和本机 Wi-Fi 配置加载，并仅向编译器传递，不在终端打印明文。

## 2. 已实现功能

- Wi-Fi STA 连接、自动重连及后台重试。
- NTP 对时。
- 基于芯片 eFuse MAC 生成唯一 MQTT Client ID。
- MQTT 断线指数退避重连，退避范围 2 至 30 秒。
- 使用车辆账号登录并订阅控制主题。
- 发布 retained 在线状态，并配置离线遗嘱。
- 接收并严格检查 20 字节控制帧。
- 每 5 秒发布 20 字节测试遥测，包含接收帧计数、运行时间和 RSSI。
- 400 ms 控制超时安全看门狗；当前网络测试固件不驱动电机。
- GPIO8 状态灯：未联网快闪、Wi-Fi 已连但 MQTT 未连慢闪、MQTT 在线短脉冲。

## 4. TLS 兼容性结论

服务器当前证书链为叶证书 → YE2 → Root YE → ISRG Root X2 → ISRG Root X1。实测 Arduino-ESP32 2.0.17 所带的旧版 mbedTLS 无法正常完成该证书链的 CA 验证，即使加载 X1、X2、Root YE 或当前叶证书仍返回验证错误。

为了在测试阶段不以明文或盲目信任方式发送 MQTT 密码，本固件采用限定方案：先建立 TLS 通道，读取服务器叶证书 SHA-256，只有它与固件内预置指纹完全一致时才发送 MQTT 登录凭据；不一致立即断开。当前指纹：

```text
4F:A4:E8:2D:D5:2A:56:D9:B0:77:78:A7:B2:FF:89:23:F8:7F:AA:93:CF:29:6A:C1:32:F4:44:35:02:43:A4:EB
```

该方式适合本次受控联调，但不应直接作为量产方案。当前叶证书有效期至 2026-09-18，证书续期后指纹会改变。正式车端接入前，应升级到更新的 Arduino-ESP32/mbedTLS 并恢复完整 CA 链和主机身份验证，或调整服务器证书链以兼容嵌入式客户端。Let’s Encrypt 证书链资料：<https://letsencrypt.org/certificates/>。

## 6. 后续接入建议

1. 先升级 ESP32 Arduino Core 并完成标准 CA 验证回归，移除测试指纹方案。
2. 联合 STM32 工程确定 20 字节正式字段、大小端、序号与校验规则。
3. 增加 ESP32-C3 与 STM32 的串口桥接，但保持 MQTT 线程不被串口阻塞。
4. 将 400 ms 看门狗接入真实停车输出，同时增加 Wi-Fi/MQTT 断线立即停车。
5. 在架空车轮或断开动力条件下完成低风险联调，再进入真车测试。
