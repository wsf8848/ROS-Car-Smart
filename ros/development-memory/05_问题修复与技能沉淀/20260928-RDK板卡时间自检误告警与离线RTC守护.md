# RDK板卡时间自检误告警与离线RTC守护

## 现象

- 板端系统时间和RTC都处于2026-09-29，相对正确日期2026-09-28超前约24小时。
- 传统`ntp.service`为active，但公网池全部`reach=0`；`timedatectl`显示未同步。
- 旧网页没有系统/RTC差值和离线可信来源，只能产生笼统时间告警。

## 根因

旧`sync-rdk-time.ps1`无条件把Windows时钟写入Linux系统时间和RTC。Windows时钟错误时，错误日期被永久写入RTC；重启后继续恢复错误时间。板端又缺少开机守护、周期状态文件和离线RTC健康判据。

## 修复

1. 把系统时间和RTC纠正到2026-09-28，写入UTC RTC。
2. 新增`bee_time_guard.py`：有效年份限定2026至2035，系统/RTC差值不超过5秒；开机最多等待RTC 20秒并用RTC恢复系统时间。
3. 新增`bee-time-guard.service`和`bee-time-check.timer`，周期为2分钟；状态原子写入`/run/bee-time-guard/status.json`。
4. 网关`/api/system/health`新增时间健康字段；网页板卡健康显示真实时间、`RTC离线可信`和差值，不把离线ntpd状态当失败。
5. 校时脚本改为必须显式指定可信UTC，或明确确认使用Windows时钟，避免再次静默污染RTC。
6. 修正未来mtime，避免Make/CMake clock skew。

## 启动顺序问题

首次版本使用`ConditionPathExists=/dev/rtc0`，整板重启时RTC节点尚未出现，systemd直接跳过守护服务。修复为等待`systemd-udev-settle.service`，并在程序内有限重试RTC；第二次整板重启后守护自动成功。

## 验证证据

- 两次整板重启测试；最终系统时间和RTC均为2026-09-28。
- `bee-time-guard.service`、`bee-time-check.timer`、`bee-web-console.service`、`bee-ld14.service`全部active。
- 周期timer于07:31:10自动执行成功，状态`healthy=true`、系统/RTC差值`0.0秒`。
- 未认证`/api/system/health`保持401；固定根网址保持认证跳转。
- Windows真实浏览器显示“板卡运行正常”“板卡时间 2026/9/28”“RTC离线可信 · 系统/RTC差 0.0秒”。
- 运动按钮继续禁用，未启用STM32、Nav2或车辆运动。

## 可复用规则

- 离线系统不能用NTP同步标志作为唯一时间健康依据。
- 绝对时间必须有可信来源；RTC只能保持已写入的时间，无法判断一个“看起来合理但实际超前”的日期。
- systemd设备条件在启动早期可能永久跳过服务；硬件出现时序不确定时用依赖加程序有限重试，并以真实重启验收。
- PowerShell远程Bash含`$变量`时用单引号传递，避免本地提前展开。
