# 任务执行器控制命令请求确认缺失

- 日期：2026-09-28
- 状态：已闭环

## 现象

- Nav2隔离仿真中，单点导航和两轮三航点巡逻均已成功；随后发送`pause`，执行器实际进入`paused`，但自动化测试等待新`request_id`超时并报告“command not accepted”。

## 根因

- 首版执行器只在`navigate/patrol_start`分支写入新请求ID；`pause/resume/cancel/retry/skip`等控制命令改变了状态，却保留上一条任务的`request_id`。
- 动作执行链与命令确认链不一致，外部网关无法可靠区分“未收到命令”和“命令已处理但状态未确认”。

## 修复与验证

- 所有合法命令在通过运动互锁后先统一写入本次`request_id`，再执行具体状态转换；失败状态也关联同一请求。
- 重新跑完整仿真：单点5.43秒完成；3航点×2轮47.38秒完成；暂停为`paused`，恢复后继续`running`，取消为`canceled`。
- 取消后`/odom`实测`linear.x=0.0`、`angular.z=0.0`；不可达占据目标返回`failed`、`last_error=nav2_status_6`。

## 可复用规则

- 异步任务接口必须为开始、暂停、恢复、取消、重试、跳过等每一种命令生成并回显独立请求ID；不能只给主任务生成ID。
- 自动化需要分别断言“命令已接收”“状态已转换”“速度归零”，三者不可互相替代。
