# 2026-09-26 RDK板端系统时间无法持久同步

## 现象

- RDK X5重启或运行后系统日期回到`2000-01-01`，当前时区为`Asia/Shanghai`。
- `timedatectl`显示`System clock synchronized: no`和`NTP service: n/a`。
- `systemd-timesyncd`为inactive，板上存在`/dev/rtc0`。

## 当前影响

- 不影响Bee ROS Web Console本次UI布局、LD14实时显示和固定网址访问。
- 会导致systemd日志、ROS记录、截图证据、文件修改时间和构建依赖判断失真。
- 已出现过Make/CMake `clock skew`风险，因此后续驱动或ROS包构建不能仅依赖异常系统时间判断是否重编译。

## 本轮处理边界

- 当前板卡无互联网，不能假设公共NTP可用。
- 本轮未擅自启用或修改系统时间服务，也未把Windows当前时间直接写入RTC，避免未经验证的系统级改动。
- UI任务继续按功能证据验收，时间异常单独登记，不将其误判为网页部署失败。

## 后续建议与验证顺序

1. 部署或调试前，由可信Windows电脑通过SSH把当前时间同步到RDK。
2. 核对RTC驱动、RTC当前值和断电保持能力，再评估`hwclock --systohc`写入。
3. 为无互联网交付环境设计开机时间来源：局域网时间源、Windows部署端同步或可靠RTC恢复，三者择一并形成脚本/服务。
4. 验证重启和完全断电上电后的系统时间、RTC时间、日志时间与ROS bag时间戳。
5. 在时间恢复前，涉及CMake/Make的关键改动使用clean构建，并校验安装二进制哈希与运行版本一致。

## 已验证修复

- 新增Windows部署端`tools\sync-rdk-time.ps1`，以Windows UTC为离线可信时间源，暂停传统`ntpd`后设置系统时间并写入UTC RTC，再恢复`ntpd`。
- 2026-09-26真实执行后，系统时间和RTC均从2000年更新到2026年。
- 真实重启RDK X5后，系统时间与RTC继续保持2026-09-26并正常走时；网页和LD14服务自动恢复，固定网址HTTP 200。
- 无公网时不以`System clock synchronized`标志作为唯一通过条件；必须同时读取系统时间、`hwclock`和重启后保持结果。

## 状态

- 已修复并通过重启持久化验证。完全断电后RTC保持能力仍需未来有条件时补做一次物理断电测试。
