# 地图生命周期 ROS2 daemon 拖住网页服务重启

- 日期：2026-09-28
- 状态：已闭环

## 现象

- 部署任务状态面板后执行`systemctl restart bee-web-console.service`，网页进入离线，服务长时间停留在`deactivating (final-sigterm)`。
- 主网关Python进程已经正常退出，但service cgroup内仍残留`ros2cli.daemon.daemonize`，systemd默认等待停止超时，发布脚本30秒内无法获得新PID。

## 根因

- 地图加载期间网关调用`ros2 lifecycle set`，Humble CLI默认可能启动常驻ROS2 daemon；该daemon继承网页服务cgroup。
- 网关退出后daemon仍存活，导致service没有立即完成停止；原单元没有显式短停止超时，发布过程看起来像重启失败。

## 修复

- 地图生命周期命令改为`ros2 lifecycle set --no-daemon ...`，不再从网页服务派生常驻ROS2 CLI daemon。
- `bee-web-console.service`明确设置`KillMode=control-group`、`TimeoutStopSec=12`、`SendSIGKILL=yes`，保证异常残留进程不会无限拖住发布。
- 首次恢复时先只读确认残留cgroup，再用受控`systemctl kill --kill-who=all --signal=KILL`清理，随后reset-failed并启动；没有盲目重复覆盖文件。

## 验证

- 修复后正式restart从旧PID 5797切换到新PID 6296，4秒内恢复HTTP登录页，服务`active/running`。
- `TimeoutStopUSec=12s`、`KillMode=control-group`已在板端生效。
- 巡逻契约测试重新通过，`bee-base-driver`、`bee-nav2-stack`、`bee-nav2-map`继续inactive；没有解除运动安全门。

## 可复用规则

- systemd服务内调用ROS2 CLI生命周期命令必须优先使用`--no-daemon`，或把CLI放入独立受控单元；不能让常驻ROS2 daemon继承长期服务cgroup。
- 发布重启必须验证“旧PID结束、新PID产生、HTTP恢复”，出现deactivating时先审计cgroup残留，不能盲目再次restart。
