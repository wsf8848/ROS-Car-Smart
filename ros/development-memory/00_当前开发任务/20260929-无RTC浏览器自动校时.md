# 无RTC浏览器自动校时

- 日期：2026-09-29
- 状态：已完成运行时自动同步；物理断电保持能力待现场验证
- 目标：即使RDK板没有可断电保持的RTC，也能在Windows访问Bee ROS Web Console时自动获得正确时间，并在运行中持续复核。

## 检查点1：板端时间源审计（已完成）

- 板端存在`/dev/rtc0`，驱动名为`hpu3501-rtc`，检查时系统与RTC只差约0.1秒。
- `timedatectl`显示`NTP service: n/a`、`NTPSynchronized=no`，当前没有可用NTP守护。
- 审计时Windows日期为2026-09-29，而板端和RTC仍为2026-09-28，实际偏差约86399.975秒。这证明“运行时有RTC节点”不等于“RTC断电保持可靠”。
- 物理断电后RTC是否保持仍未验证，不再把RTC作为唯一可信源。

## 检查点2：多源时间守护与受限同步助手（已完成）

- 新增`tools/bee_time_sync_helper.py`，安装为root拥有的`/usr/local/sbin/bee-time-sync`。
- 助手只接受`--epoch-ms <整数> --source browser`，校验2026~2036合法范围；存在近期可信同步记录时拒绝超过48小时的异常跳变。
- 时间优先级固定为：已同步NTP → 最近Windows浏览器可信时间 → 可用RTC → 上次可信时间文件 → 未验证系统时间。
- `bee_time_guard.py`改为RTC可选：开机从系统、RTC和`/var/lib/bee-time-guard/last-trusted-sync.json`中选择最新合法时间，防止无后备RTC时倒退；运行中每2分钟复核来源和新鲜度。
- 新增严格sudo规则`deploy/bee-time-sync.sudoers`，只允许`sunrise`调用固定助手；`visudo -cf`验证通过。浏览器不能拼接或执行任意命令。

## 检查点3：网页登录自动同步（已完成）

- 新增认证保护、同源限制的`POST /api/system/time-sync`，请求体严格为`epoch_ms/timezone_offset_min`。
- 管理员登录控制台后自动用Windows浏览器`Date.now()`同步；页面可见时每10分钟复核，窗口从后台恢复时也会检查。
- 前端资源版本提升为`20260929-timesync1`。
- 板卡健康窗口按真实来源显示“NTP自动同步”“Windows浏览器自动校时”“RTC离线回退”“上次可信时间回退”或“系统时间未验证”。

## 检查点4：真实板端验证（已完成）

- 刷新已登录网页后，网关真实记录`BEE_TIME_SYNC_AUDIT`，来源`browser_sync`，客户端为Windows浏览器；未登录POST返回401。
- 手动触发`bee-time-check.service`后状态仍为`healthy=true/source=browser_sync`，没有被RTC回退；系统/RTC差约0.282秒。
- 浏览器“板卡健康”实测显示`2026/9/29 08:32:04`和“Windows浏览器自动校时 · 系统/RTC差0.3秒”。
