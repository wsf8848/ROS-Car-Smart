# RGB摄像头识别与网页实时画面

- 日期：2026-09-27
- 状态：进行中
- 用户目标：识别当前接入RDK X5的WHEELTEC C100/C70 RGB摄像头，打通实时画面并接入Bee ROS Web Console；网页使用显式“摄像头”入口，打开为大画面并支持最小化。

## 检查点1：资料与基线审计

- 资料目录包含C100产品规格/GC2053手册、C70产品规格/JX-H62手册、USB摄像头标定和Python OpenCV例程。
- 厂家例程按较小的新增`/dev/videoN`打开UVC摄像头；该规则仅作参考，最终必须用板端USB描述符、V4L2设备能力、真实取帧交叉确认。
- 网站当前正式布局为顶部车辆状态、地图主区、右侧控制栏；地图和LD14已有主画面/最小化交互，新增摄像头应复用该交互模型，避免在右侧控制栏常驻视频挤压操作区。
- 实施选择：增加“摄像头”视图按钮；点击后摄像头占满地图主区域，提供最小化按钮恢复地图。默认不开流/不占带宽，进入视图时加载，离开时释放浏览器请求。
- 保护边界：不启用车辆运动；不改蓝牙/MQTT/STM32协议；不影响LD14与地图视图；认证用户才能访问视频；不把摄像头型号仅凭资料文件名写成实测结论。

## 检查点2：板端型号与V4L2能力确认

- USB实测：`0bda:3031 Realtek Integrated Webcam`，UVC 1.00，序列号`200901010001`。
- 稳定节点：`/dev/v4l/by-id/usb-Generic_Integrated_Webcam_200901010001-video-index0`指向`/dev/video0`；`video1`仅有Metadata Capture能力，不能作为图像节点。
- `/dev/video0`最高且默认为MJPEG 1280x720@30fps；YUYV 1280x720最高10fps，另支持640x480@30fps等。
- C70资料标称JX-H62、100万像素、最高1280x720、YUY/MJPEG；C100资料标称GC2053、200万像素、最高1920x1080。结合板端只枚举到720P，当前实物判定为WHEELTEC C70；USB字符串本身为通用名称，型号结论来自规格与V4L2能力交叉核验。
- 选择原生MJPEG输入，避免使用YUYV造成USB带宽和CPU负担；网页首期目标1280x720、约20-30fps，实测负载后再定最终帧率。

## 检查点3：视频链路与认证接口完成

- 最终链路：`C70 /dev/video0 MJPEG 1280x720@30 -> FFmpeg -> MJPEG 960x540@15 -> Bee同源HTTP multipart -> Windows浏览器`。
- 网关新增`/api/camera/status`与`/api/camera/stream.mjpg`；两者均复用网站登录会话，未登录实测均返回HTTP 401。
- 采集使用稳定路径`/dev/v4l/by-id/usb-Generic_Integrated_Webcam_200901010001-video-index0`，而不是依赖可能变化的`/dev/video0`编号。
- 多浏览器请求共享单个FFmpeg采集进程；没有客户端时不启动采集，最后一个客户端退出后停止FFmpeg、释放USB设备和网络带宽。
- 输入原生MJPEG，网页输出实测平均带宽约3.21Mbps；最终选择960x540@15fps，在监控清晰度、RDK负载与热点带宽之间留出导航数据余量。

## 用户确认的摄像头产品定位与后续能力边界

- 2026-09-27用户确认：C70的首要用途是小车执行建图、导航和巡逻时，将前方真实画面低延迟传到Bee ROS Web Console，供操作者观察、人工接管和交付演示；该能力已经打通。
- 当前二维自主导航继续以LD14、轮速里程计和IMU为主，RGB视频断开不应导致Nav2停止；反过来，视频在线也不能冒充定位或避障有效。
- C70可以扩展传统视觉循迹：识别地面高对比色带/黑线，计算横向偏差和方向后生成速度修正。该模式需要固定相机安装角度、地面ROI、曝光、线路颜色和速度上限，并作为独立“视觉循迹模式”接入控制权仲裁，不能与Nav2同时直接控制底盘。
- RDK X5的BPU可以扩展目标检测、人员/车辆识别、二维码/标志牌识别、区域入侵告警和巡逻抓拍。实际可用性取决于模型转换、720P画质、光照、安装位置和实体数据集验证；未经模型和实车测试不得标记为已完成。
- 单目C70没有直接深度信息，不作为当前近障安全传感器；LD14和STM32安全保护仍负责主要避障。仅靠单目框大小估距可靠性不足，不得直接用于安全停车距离。
- 视觉里程计、视觉SLAM或语义导航属于后续高级扩展，计算、标定与环境要求明显高于实时监控和目标检测，不纳入当前四项ROS交付功能的前置范围。

## 检查点8：修复RGB摄像头“最小化后消失”

- 用户反馈：点击“最小化画面”后，RGB画面直接消失，没有像LD14一样保留可见的小窗入口。
- 根因：旧版只在`.map.camera-expanded`时显示`.camera-view`；最小化会移除`camera-expanded`、把`img.src`切到透明占位图并停止流，因此视觉上完全隐藏。
- 修复：新增`cameraVisible`、`camera-visible`和`camera-minimized`状态。进入RGB主视图时开启视频；点击最小化后退出主视图但保留右下角250×150实时小窗，继续保持同一个MJPEG客户端；点击小窗任意位置可重新放大。页面关闭时仍调用`setCameraStreaming(false)`释放连接和FFmpeg。
- 小窗位置与LD14错开：LD14默认在右下偏上区域，RGB小窗在右下角；窄屏自适应为190×116，不挤压右侧控制栏。
- 状态提示：最小化后角标显示“实时小窗”，小窗底部显示“点击放大 RGB 画面”，不会再出现无入口的消失状态。
- 验证：本地`node --check frontend/live.js`、前端构建通过；板端`bee-web-console.service`重启后Playwright验收通过。1440×1000主画面自然尺寸960×540；最小化后`camera-visible=true`、`camera-minimized=true`、小窗250×150、`display:flex`、`/api/camera/status clients>=1且online=true`；1024×900无横向溢出；1536×768人工接管/巡逻仍在首屏；浏览器控制台0错误；LD14主画面/最小化回归通过。
- 新验收截图目录：`Bee ROS Web Console/artifacts/camera-minimize-fix`（由自动化测试生成）。

## 检查点9：修复板端重复加载导致的现场显示异常

- 现场复测发现：生成的`frontend/index.html`同时加载了两份`live.css`和两份`live.js`。原因是构建脚本只移除不带查询参数的源片段标签，而源片段被加上版本参数后未被移除，导致摄像头DOM和事件初始化两次。
- 修复`tools/build-frontend.ps1`：移除`live.css`/`live.js`标签时同时兼容`?v=...`，并将默认资源版本提升为`20260927-camera3`。
- 重新构建后确认生成页面各只有一份资源：`/live.css?v=20260927-camera3`、`/live.js?v=20260927-camera3`；重新部署并重启`bee-web-console.service`。
- 板端最终实测：摄像头主视图正常；点击最小化后唯一小窗`280×176`、`display:flex`、`camera-visible=true`且`camera-minimized=true`，视频`clients=1/online=true`；1024×900无横向溢出、1536×768控制区首屏完整、控制台0错误。
