## 2026-09-27 UART5_TX复用语音模块评估

- 正式副本源码实查：`Hardware/Lidar.c`把PC12配置为UART5_TX复用推挽、PD2配置为UART5_RX，并以`USART_Mode_Rx | USART_Mode_Tx`启用230400-8-N-1；UART5只有RXNE雷达接收中断。
- 应用源码中不存在`USART_SendData(UART5, ...)`、UART5发送函数或UART5 TX中断，因此PC12当前是“硬件已初始化、业务未发送”，不参与LD14数据接收。
- UART5发送与接收共用同一波特率、字长、校验和停止位。PC12只有在语音模块支持230400-8-N-1且只接收指令时，才可考虑连接到语音模块RX；接线为PC12 -> 语音模块RX并共地，必须先核验双方TTL电平。
- 禁止为了常见9600/115200语音模块在播放前临时改UART5波特率再切回：切换期间会丢失LD14连续数据、破坏47字节帧同步并可能触发300ms雷达超时停车。
- USART3默认PB10/PB11在本板已被电机方向控制占用，不能直接作为语音串口；UART4、USART2、USART1也分别承担ESP32-C3、蓝牙和RDK通信，不能未经资源审计复用。
- 如果语音模块不支持230400，优先方案是选择经原理图确认的空闲GPIO实现独立仅TX软件串口，或由RDK X5的独立UART/USB转串口控制。待用户提供语音模块型号、供电/TTL电平、默认波特率和发送协议后再确定接线并修改独立工程副本。
- 本检查点仅完成源码与资源评估，没有修改STM32代码、没有重新编译，也没有进行语音模块实物验证。

### 2026-09-27 LD14波特率资料复核

- 随设备原厂`LD14激光雷达开发手册_v1.3.pdf`串口章节写明标准LD14为115200bit/s、8位数据、1停止位、无校验、无流控；`LD14激光雷达数据手册.pdf`同样标注`UART@115200`，并说明上电稳定后自动发送测量数据、不需要任何指令。
- 原厂Python示例与Windows上位机说明也使用115200；资料包未提供把雷达从230400改到115200的配置指令，因此不能把它当成运行时可配置功能。
- 但本项目当前实体设备曾在RDK端以230400连续读到`54 2C`、47字节完整帧，STM32正式副本也据此配置230400。该差异可能来自实物批次、OEM版本或型号标识差异，不能仅按资料文件名覆盖实测基线。
- 后续如需让UART5整体改为115200以复用TX，必须在隔离测试中分别以115200和230400抓取原始数据，比较固定帧头、47字节分帧、CRC8正确率和连续帧频率；只有115200连续通过后才能同步修改STM32与RDK配置。未验证前保持230400，禁止只改单侧。

### 2026-09-27 原理图串口3/串口4与新增单向TX审计

- 原理图`一体板原理图.pdf`显示H4“串口引出”为2x4插座：1=PD2、2=GND、3=PC12、4=PC13、5=PC11、6=PA2、7=PC10、8=PA3。H4本身没有电源脚，外接语音模块需从独立供电引出取电并与H4-2共地。
- USART3默认引脚PB10/PB11已作为右前轮电机C的两个方向控制脚；USART3部分重映射PC10/PC11与UART4冲突；全重映射PD8/PD9没有出现在本板H4且不作为当前可用引出。因此USART3不能在不牺牲电机或UART4的前提下复用。
- UART4并非空闲：PC10/TX、PC11/RX已由`Esp32Link`以115200初始化，PC10在每个遥测周期发送0x51雷达、0x53电池和0x52底盘帧，PC11接收ESP32-C3/MQTT控制；历史报告已有UART4双向实链证据。复用PC10给语音模块会让语音模块持续收到车辆二进制遥测，且可能破坏原MQTT链路，不允许这样并接。
- UART5的PC12/TX目前业务未发送，但UART5与PD2雷达RX共用通信参数；只有语音模块接受实体雷达最终验证波特率时才可使用，不能独立设成另一波特率。
- PC13从原理图直接引到H4-4，当前正式源码未配置或使用PC13，也不与四轮电机、ROS、蓝牙、ESP32-C3、LD14或ICM42670冲突。对于“语音模块只接收、发送数据很少”的需求，优先候选为PC13实现定时器驱动的单向软件UART TX。
- PC13软件TX只连接高阻TTL RX，短线、共地并先核验3.3V电平；建议优先9600或模块默认低速率。若模块固定115200，必须评估UART5高优先级230400接收中断下的软件串口定时抖动，不能只靠阻塞延时位翻转。
- 本检查点仅完成原理图和源码审计；未修改代码、未编译、未接语音模块。实施前仍需模块型号、供电、逻辑电平、波特率和帧协议。

### 2026-09-27 PC13单向软件串口实现建议

- 软件串口是由普通GPIO按UART时序主动输出电平，不占用STM32硬件USART/UART外设。当前需求只发送少量十六进制语音控制帧，不需要RX，适合实现为单向TX。
- 8-N-1发送格式固定为：空闲高电平 -> 1位低电平起始位 -> 数据位D0到D7低位先发 -> 1位高电平停止位。9600波特率每位约104.17微秒，每字节10位约1.04毫秒。
- 推荐用硬件定时器中断驱动状态机：应用层只把完整命令放入发送队列；定时器每个比特周期更新PC13一次；发送完成自动停止定时器并把PC13恢复高电平。禁止在主循环用长时间`Delay_us`关中断阻塞发送，以免影响UART5雷达、编码器和电机控制周期。
- 对本项目而言，PC13短线连接高阻语音模块RX、3.3V TTL、9600-8-N-1并偶发发送短帧，预期可靠性高；最终仍必须用逻辑分析仪/示波器核对位宽和实际模块连续播放测试。115200每位仅约8.68微秒，在230400雷达高优先级接收中断下风险明显更高，不作为首选。
- 驱动应提供`VoiceUart_Init()`、`VoiceUart_Send(const uint8_t*, uint8_t)`、忙状态与有界队列；同一提示加冷却/去重，禁止在中断内组帧或连续重复播报。具体帧头、命令、校验和帧间隔以语音模块手册为准。
- 本条为设计方案，尚未写入STM32源码或进行编译/硬件验证；取得语音模块资料后从1-29复制新副本再实施。

#### 定时器资源复核

- 当前正式固件：TIM1通道4+DMA驱动WS2812；TIM2、TIM3、TIM4、TIM5分别用于四路正交编码器；TIM6用于1ms系统节拍和蜂鸣器/10ms调度；TIM8用于四路电机PWM。
- TIM7在当前源码中没有初始化、没有中断函数、没有业务占用，可作为PC13单向软件UART的独立位时钟，不需要修改上述现有定时器配置。
- 推荐TIM7按语音模块波特率产生更新中断，ISR只执行PC13置位/复位、位下标推进和结束判断；不在ISR内组帧、延时、打印或调用业务逻辑。9600波特率下5字节8-N-1命令约5.2ms，只在发送期间产生约50次短中断，平均系统开销很小。
- 中断优先级必须保留UART5雷达为最高优先级，并让TIM7 ISR足够短；代码完成后仍需同时压测雷达CRC/丢帧、四轮编码器、电机PWM、蓝牙/MQTT/ROS通信和语音连续触发，验证通过后才能写成“不影响其他控制”。
